## 1. Custom subagents in the IDE agent

**Source:** [Subagents](https://cursor.com/docs/subagents)

- Defined as Markdown files with YAML frontmatter in `.cursor/agents/` (project) or `~/.cursor/agents/` (user). `.claude/agents/` and `.codex/agents/` are also read for compatibility; `.cursor/` wins on name conflicts, and project beats user.
- Subagents work in the editor, CLI, and Cloud Agents.

Frontmatter fields (all optional):

| Field | Type | Default | Meaning |
|---|---|---|---|
| `name` | string | filename | Identifier (lowercase + hyphens); invoked via `/name` |
| `description` | string | — | Shown to the parent to decide delegation |
| `model` | string | `inherit` | `inherit` or a specific model ID, optionally with `[id=value,...]` params |
| `readonly` | boolean | `false` | No file edits / state-changing shell |
| `is_background` | boolean | `false` | Runs without blocking the parent |

Exact format:

```markdown
---
name: security-auditor
description: Security specialist. Use when implementing auth, payments, or handling sensitive data.
model: inherit
readonly: true
is_background: false
---

You are a security expert auditing code for vulnerabilities.
...
```

Model with parameters:

```markdown
---
name: planner
description: Plans complex changes before implementation.
model: claude-opus-5[effort=high,context=300k]
---
```

- **Own model:** yes. `model` can be a specific ID (docs examples: `composer-2`, `gpt-5.6-sol`, `claude-opus-5[effort=high]`). The 3.3 changelog also added family aliases like `model: opus` ([changelog 05-07-26](https://cursor.com/changelog/05-07-26)).
- **Background / parallel:** yes. `is_background: true` in frontmatter, or the parent launches multiple Task tool calls in one message so they run concurrently. Background subagents write state to `~/.cursor/subagents/` and can be resumed by agent ID. Isolated worktrees per subagent are available on request ("each in its own environment"). Nesting is allowed one level deep (main → subagent → child subagent, no further) since Cursor 2.5.

## 2. Delegating to a cheaper model

**Source:** [Subagents › Model configuration / Parent model and usage pools](https://cursor.com/docs/subagents)

- Yes. The model picker (including Auto) applies only to the parent. A subagent can run a different model via (a) `model:` frontmatter, (b) the parent naming a model when it launches the Task, or (c) built-in subagents picking their own (Explore uses a faster model by default; its model is also configurable in settings per the 3.3 changelog).
- Billing is per model actually run, at list price; the task card and usage dashboard show which model ran.
- **How the allowed list is determined:** the docs don't publish a dedicated "subagent-allowed" list. The `model` field is honored unless: a team admin has blocked the model (Team Settings › Models), the plan doesn't include it, or a legacy request-based plan requires Max Mode and it's off. In those cases Cursor falls back to the parent's model and notes this in the subagent result ([CLI changelog v2026.10.22](https://cursor.com/docs/cli/changelog)). On legacy request-based plans without Max Mode, subagents always run Composer. Valid IDs come from the [models reference](https://cursor.com/docs/models-and-pricing); the docs say options "use the same `id=value` pairs as the SDK's model parameters."
- **Not confirmed in docs:** whether the IDE exposes a per-session UI list of subagent-eligible models. Effective eligibility is plan + admin policy + model catalog, not a per-session setting.

## 3. Multitask mode

**Sources:** [What is multi-agent coding?](https://cursor.com/help/ai-features/multi-agent) (help center), [changelog 3.2](https://cursor.com/changelog/04-24-26), [changelog 3.3](https://cursor.com/changelog/05-07-26)

- `/multitask` makes Cursor run your requests as **async (background) subagents in parallel** instead of queuing them, and it can split a large task into chunks for a "fleet" of subagents. Already-queued messages can be converted to multitask.
- Enabled by typing `/multitask` in the chat input (Agents Window from 3.2, editor from 3.3). From a plan, **Build in Parallel** triggers the same mode and keeps dependent steps ordered.
- Relationship: it is a front-end for subagents (background mode); it is not Cloud/background agents. Cloud subagents are a separate path (`/in-cloud`, `/autopilot`) that run on their own VM.
- **Flag:** there is no dedicated docs page for Multitask; only the help article and changelog. Model selection for multitask subagents isn't documented (a forum post says they mostly use the parent model, but that's not official docs).

## 4. Cursor CLI (`agent`)

**Sources:** [Parameters](https://cursor.com/docs/cli/reference/parameters), [Headless](https://cursor.com/docs/cli/headless), [Using](https://cursor.com/docs/cli/using), [CLI changelog](https://cursor.com/docs/cli/changelog)

- **Subagents:** yes. "Subagents in the CLI" shipped March 2026; they run in interactive, headless, and ACP sessions and inherit credentials, rules, and approval policy. Custom `.cursor/agents/*.md` files are honored, including `model:` (the v2026.10.22 CLI entry describes pinned-model fallback behaviour, confirming the CLI reads it). Headless runs wait for subagents to finish before exiting (v2026.08.11).
- **Model flag:** `--model <id>`; list what's accepted with `agent models` or `--list-models`. Team model restrictions apply (a blocked `--model` exits with the restriction message). Model variants/params work headless (e.g. fast / high-effort slugs). The interactive equivalent is `/model`.
- **Different model for subagents:** yes via frontmatter `model:` or by naming a model in the prompt; the Explore subagent's model is configurable in `/config`.
- **Non-interactive:** `-p` / `--print`, with `--output-format text|json|stream-json`, `--stream-partial-output`, `--force`/`--yolo` to apply edits, `--trust`, `--workspace`, `-w/--worktree`, and `CURSOR_API_KEY` for auth:

```bash
export CURSOR_API_KEY=...
agent -p --force --model "gpt-5.6-sol" --output-format json "refactor X"
agent -p --model "composer-2.5" --workspace ~/repo -w "fix tests"
```

So a script can spawn several `agent -p --model ...` processes and orchestrate them itself. Note the docs caution about concurrent CLI processes writing `cli-config.json` (fixed with atomic writes in v2026.07.06); `--worktree` is the documented way to isolate parallel runs.

## 5. Cursor SDK (`@cursor/sdk`)

**Source:** [TypeScript SDK](https://cursor.com/docs/sdk/typescript)

- Each `Agent.create()` takes its own `model: { id, params? }`, so a script can create N agents with N models and orchestrate them in plain TypeScript (`agent.send()` → `run.wait()` / `run.stream()`; `Promise.all` for parallelism). The docs explicitly list "orchestrators" as a target use case and show a dispatcher pattern. Per-run overrides: `agent.send(msg, { model })` (sticky).
- Built-in delegation: pass `agents: { name: { description, prompt, model } }` on `Agent.create()`; `model` is `"inherit"` or a `ModelSelection`, so a parent on one model can spawn subagents on another. File-based `.cursor/agents/*.md` are also loaded. Nesting is one level deep; background subagents return results as follow-up turns (local only).

```typescript
const parent = await Agent.create({
  apiKey, model: { id: "claude-opus-5" }, local: { cwd },
  agents: {
    "explorer": { description: "Fast codebase search", prompt: "...", model: { id: "composer-2.5", params: [{ id: "fast", value: "true" }] } },
  },
});
```

- **Model discovery:** yes, `Cursor.models.list()` is the documented source of truth for valid ids, `parameters`, and preset `variants` (account- and team-specific; `isMaxMode` flagged on variants since SDK 1.0.38). The docs say "discover, don't hard-code." Invalid ids throw `ConfigurationError`. Pass `teamId` (1.0.40+) if you belong to multiple teams.
